## 优先修复：已经复现的逻辑问题

### A01 / P1：时间线详情不识别演员片段内的手工骨骼动画

触发：在 Spawn 片段里首次应用姿态或建立手工骨骼关键帧，再选中演员轨道查看骨骼详情。

`ActorAnimationEditContext` 会遍历 `ActorEmbeddedAnimation.clips(...)` 并优先解析 Spawn 内的修正层；`ActorAnimationDetailTarget.resolve` 却只遍历 payload 中直接存在的 `EntityAnimationClip`。同一个演员在两个解析器中分别得到“可以编辑”与 `NO_ANIMATION`。

结果：详情面板只进入“无动画”的画廊分支，不能正常进入完整骨骼属性与 dope sheet 分支。上一轮把画廊加入空状态，未解决其目标解析不一致。

复现结果：预期 `READY`，实际 `NO_ANIMATION`。

位置：`ui/actor/pose/ActorAnimationDetailTarget.java:37`、`ActorAnimationEditContext.java:25`、`ActorTimelineAnimationPanel.java:55`。

修复方向：共享包含“可见片段所有者”的解析结果，保留显式选中、静音、锁定及重叠片段的现有保护。不能只把循环换成 embedded 列表而忽略 wrapper 所有权。

### A02 / P1：镜像仍是六部位逻辑，缺少肘膝；选中范围也不明确

`ActorAnimationAuthoringService.mirror` 只列出 body/head/双臂/双腿，未列入 forearm/shin。可弯曲玩家已是当前玩家骨架，但镜像仍按旧骨架操作。

复现：右肘在 1 秒有弯曲关键帧，执行镜像后，左肘没有任何对应关键帧。

此外，dope sheet 的“镜像”从选中键只提取时间，再写入六个部位的旋转。只选中一个部位，仍可能新增或覆盖其他部位的键；位置和缩放选中键也不能从按钮名称判断实际行为。

位置：`ui/actor/pose/ActorAnimationAuthoringService.java:137`、`ActorAnimationDopeSheet.java:210`、`:603`。

修复方向：分开“镜像所选部位”和“镜像全身姿态”，按骨架对称映射处理肘膝及弯曲编码，并明确覆盖已有目标键的规则。

### A03 / P1：新建整体变换片段不能保持当前状态连续

`ActorTrackClipAuthoringService.createTransformClip` 从 Spawn 的静态位置／yaw／pitch 取初值；roll 固定为 0，缩放固定为 1。没有从播放头当前采样结果接续。

复现：Spawn 的缩放为 `(2,3,4)`，新建 Transform 的起始缩放变为 `(1,1,1)`。代码也明确把 roll 归零；如果前段存在整体动画，位置和朝向也存在接续跳变风险。

位置：`ui/actor/track/ActorTrackClipAuthoringService.java:89`、`:132`。

修复方向：从同一时间的有效整体状态取完整 TRS；若当前由路径／关系控制，先使用既有冲突规则确定是否允许创建。验收应包括新建瞬间画面不跳变。

### A04 / P2：播放速度允许 0，但采样实际使用 0.01

独立动画片段属性的速度滑块与模型允许 0；`ActorAnimationLayerSample.sample`、运行时、编辑上下文及关键帧投影使用 `max(.01, speed)`。

复现：速度 0、片段本地时间 100 秒，采样到资产第 1 秒的旋转，而不是停在第 0 秒。

位置：`ui/properties/adapters/EntityAnimationClipPropertyAdapter.java:24`、`timeline/playback/entity/ActorAnimationLayerSample.java:17`。

修复方向：统一语义。可以将可调最小值统一为 0.01，也可以正式支持冻结；不能让 UI 显示 0 而内部持续推进。反向播放是另一个功能，不应靠负数速度顺便引入。

## 代码链路可确认的问题

### A05 / P1：“放置已有演员”实际重新创建演员

演员列表右键“放置”调用 `ActorSelectionHub.beginPlace(actor)`；ActorPickController 确认位置时，只把 name/type 交给 `startPlacement`。后者创建全新临时 Actor，落点后再 `actorRegistry.createActor(...)` 创建另一个正式 Actor。

这条路径不携带原演员 ID、皮肤、自定义骨架或动画引用。它更接近“用同名同类型新建一个演员”，与“放置这个演员”的交互语义不符。实际预览效果还需客户端验收。

位置：`ui/actor/pick/ActorPickController.java:233`、`ui/actor/placement/ActorPlacementController.java:107`、`:326`。

修复方向：区分新建、重新放置、复制。重新放置必须沿用原演员身份；复制应明确保留哪些项目属性和动画引用。

### A06 / P1：放置类快捷操作绕过命令与部分上下文规则

正式落地的 `ActorPlacementController.placeActorAt` 直接创建 Actor、轨道、Spawn，再 markDirty；并没有把它们作为一个撤销事务提交。

“放到摄像机位置”也直接修改／新增 Spawn。它使用演员引用轨道列表中的第一条，而非统一选择解析器；没有走既有整体变换编辑服务。已有位置关键帧、路径或重叠片段时，修改 Spawn 的静态值未必改变当前画面。

该方法检查了轨道锁定，但本地路径没有完整的播放／拖动／静音校验。不能将“这个入口没有统一检查”扩大解释为所有编辑器都没有保护。

位置：`ui/actor/placement/ActorPlacementController.java:302`；`ui/properties/adapters/ActorProjectPropertyAdapter.java:1158`、`:1190`、`:1217`。

修复方向：共用明确的目标解析和命令服务；新建演员一次撤销应同时移除其轨道与初始片段。重新定位需明确作用于播放头关键帧还是初始位置。

### A07 / P2：路径入口的目标歧义与提交方式不一致

`ActorPathMovementPropertyUI.render` 在绘制前直接调用会抛异常的 `resolveActorTrack`，没有就地处理歧义。一个 Actor 有多条候选轨道且没有唯一选择时，难以得到可操作的轨道选择反馈。

已有路径时，在下拉框选择候选就立即 `switchPath`，下方又有“切换”按钮。用户不能从界面判断下拉框是在预选还是已经提交。

位置：`ui/properties/actor/ActorPathMovementPropertyUI.java:23`、`:46`、`:61`。

修复方向：在入口显示明确的轨道选择／不可用原因；统一采用立即应用或预选后提交的一种方式。

## 动画逻辑与操作意图之间的缺口

### B01 / P1：全身静态姿态可能让后来绑定的动作完全不可见

上一轮画廊默认使用全身范围。应用静态姿态会为所选可旋转骨骼写键，包括预设中保持中性的部位。随后绑定 Wave／Attack，原手工层以默认覆盖权重保留。

求解顺序是预设 → 快速姿态 → 手工关键帧 → 脚底接触。因此全身手工旋转可以盖住新绑定动作。这是现有合成规则的预期结果，但入口只提示“保留手工关键帧”，没有明确展示“新动作被哪些通道覆盖”。不能简单删掉手工动画来让预设看起来生效。

位置：`ui/actor/pose/ActorPoseGallery.java:77`、`ActorPoseGalleryEditing.java:33`、`actor/runtime/ActorPoseEvaluator.java:39`、`:51`。

建议：绑定前检测相关通道的覆盖，显示实际受影响部位；提供明确的“保留修正”和“暂时旁路修正以预览”操作，并接入现有协调反馈。

### B02 / P2：“当前时间应用”与首个关键帧向前保持的差异未说明

首个姿态键若写在片段中部，`KeyframeTrack.sample` 会在它之前也返回首键值。因此“在 3 秒应用坐姿”可能使 0—3 秒也显示坐姿，而不是只从 3 秒变化。

这符合当前通道插值规则，不宜一概认定为采样错误。缺的是可预测的创作入口：新增动作开始时是否保留前一姿态、是否插入过渡起点、还是有意建立全段姿态。

位置：`actor/animation/asset/KeyframeTrack.java:44`、`ui/actor/pose/ActorPoseGalleryEditing.java:40`。

### B03 / P2：“自动关键帧”开关与实际提交行为不一致

姿态工具显示通用“自动关键帧”，提示关闭后使用应用按钮。但 Gizmo 松开时，只要是 animationGesture 就无条件应用，开关只影响快速姿态一侧。骨骼属性内已有更准确的“快速姿态自动应用”文案，两个入口仍不统一。

位置：`ui/properties/adapters/EditorToolPropertyAdapter.java:209`、`ui/actor/pose/ActorBoneGizmoController.java:322`、语言键 `gui.director.actor.bone_draft.hint`。

建议：按当前编辑目标显示真正生效的选项与提交方式。

### B04 / P2：共享资产提示缺少就近的解决操作

画廊会提示引用数量，但“应用姿态”仍直接写入解析出的资产。制作独立副本的能力已经存在，只是分散在资产库／预设检查器内，且预设副本与手工动画副本并非同一个对象。

建议：在写入目标旁提供针对该目标的“仅此引用制作副本”，显示是预设层还是手工层；不要要求用户依据资产 ID 自行判断。

### B05 / P2：个人姿态的撤销与文件刷新策略不一致

新增姿态 `add` 直接落盘；重命名和删除通过时间线命令执行。保存后按 Ctrl+Z 会撤销此前的时间线操作，而非刚才的新增姿态。

此外，当前文件只在路径切换时加载；重命名／删除检查外部修改后要求重新加载，但 UI 没有对应刷新入口。新增路径也没有与重命名／删除同等的外部修改检查。

位置：`ui/actor/pose/ActorSavedPoseLibrary.java:52`、`:62`、`:104`。

建议：先决定库操作是否进入统一历史，并统一显示；提供受控刷新／读取失败状态，避免把库操作和场景编辑混成不可预测的 Ctrl+Z 顺序。

## 后续能力缺口：不与上述缺陷混在一起排期

1. **多表演层与动作拼接。** Spawn 只有一个预设绑定，普通重叠 Animation 片段选取最后生效项。已经有预设／快速姿态／手工层合成，不等于用户可以任意叠加多个独立表演。后续应设计显式层序、通道占用、交叉淡化和时间段切换。
2. **更完整的时间重映射。** 当前主要是片段起点、正向速度和循环。源动画起始偏移、局部裁切、反向播放及循环相位控制尚不完整；这些应共享一套采样与编辑时间映射。
3. **可编辑曲线和过渡控制。** 当前通道有 STEP／LINEAR／SMOOTH，已有关键帧插值编辑；尚无完整切线／缓入缓出曲线编辑体验。
4. **最终姿态／程序动作烘焙。** 个人姿态明确只保存动画层旋转。路径步态、脚底接触和注视结果变为可编辑骨骼动画，仍需要专门的烘焙功能，不能把“保存当前姿态”改名后假装具备该能力。
5. **非玩家骨架和重定向。** 村民、四足类型仍没有对应的独立骨架动画编辑。普通人形与可弯曲玩家的资产跨骨架复用也需要明确映射，不应放宽兼容检查直接混用。
6. **手脚目标控制。** 现有脚底 IK 主要用于路径接触修正，不等于有完整的动画师手脚目标、固定接触区间和可视化控制器。

本轮不建议优先添加第三种关节外观、更多预设数量或剧情气泡。这些不会解决编辑目标、连续性、镜像和历史的不可靠行为。预设包分享继续排除。

## 建议实施顺序

1. 统一动画／片段所有者解析，修复 A01；修复变换接续与完整镜像 A02/A03；统一速度语义 A04。
2. 整理新建／重放置／复制及摄像机定位入口，统一命令和轨道目标，修复 A05/A06/A07。
3. 补上“动作被修正层覆盖”的检测和旁路预览，统一自动应用文案与共享资产独立副本入口。
4. 统一个人姿态历史，完善不可用原因、搜索状态、目标定位与路径影响预览；完成客户端布局与拾取验收。
5. 再按短片创作需求推进动作拼接、时间重映射、事件标记和烘焙。

首轮验收应以四个已复现用例转为通过、放置一次撤销完整恢复、应用姿态后绑定动作有明确覆盖反馈为准。不要用“测试总数通过”代替这些具体创作场景。

## 第二轮深入审查：新增五项复现

在同一基线继续检查了播放／编辑时钟、重叠片段、事件和 Gizmo 的目标选择。以下五项由独立的 `ActorAnimationDeepAuditProbeTest` 复现，不是上一轮四项的重复描述。用例仍位于 build 目录，按期望行为断言，五项均失败；结果保存在 `build/actor-audit-results/deep-probe-results.xml`。未修改业务代码。

### C01 / P1：Gizmo 与数值面板可能编辑不同的动画资产

场景：同一演员存在 Spawn 内手工修正动画，随后另有一段开始时间较晚的独立骨骼动画；选择演员轨道。

- 数值编辑上下文明确优先 Spawn 内修正层。
- Gizmo 的 `findActiveAssetClip` 独立遍历候选，只按开始时间选择较晚的动画，没有采用相同的修正层优先规则，也没有采用数值编辑器的显式引用优先规则。

复现：数值上下文指向 manual-layer，Gizmo 目标解析函数却返回 later-action。检查的是 Gizmo 实际调用的私有选择函数；尚未进行游戏内拖动验收。

这比“面板信息不一致”更严重：修改身体的同一个部位，拖动与数值输入可能写进不同资产，后者还可能是共享资产。

另外，Gizmo 的 `resolveTrack` 遍历 `model.getTracks()` 并选择首个匹配演员的轨道；数值编辑器采用支持显式选择和歧义拒绝的统一解析器。多轨道、嵌套轨道情形需要同批补充验收，不能靠修复动画优先级顺带假设全部解决。

位置：`ui/actor/pose/ActorBoneGizmoController.java:671`、`:683`；`ActorAnimationEditContext.java:34`。

建议：建立统一的骨骼编辑目标描述，包含轨道、可见片段所有者、实际动画引用和资产；数值、Gizmo、时间线详情及命令全部消费这一结果。

### C02 / P1：路径距离驱动步态时，显示相位与编辑时间不一致

场景：独立项目动画声明为 LOCOMOTION，沿路径行进，并在当前场景时间编辑其骨骼。

运行时通过 `ActorPresetClock.resolve` 把播放时间转换成行进距离相位；`ActorAnimationEditContext.capture` 与 Gizmo 的键时间仍使用 `(场景时间－片段起点)×速度`。

复现：同一个场景时刻，运行时显示资产的 **0.5 秒**，编辑上下文却指向资产的 **1.0 秒**。

因此，用户对当前看见的抬脚姿态进行修改，可能写到另一帧。单纯在 UI 增加“距离时钟”提示不足以修复误写；时间线键的映射、数值采样、草稿预览和提交位置需要一致。

适用边界：该用例针对可直接编辑的项目 LOCOMOTION 引用；默认新建的手工修正资产通常为 PERFORMANCE，不代表所有手工关键帧都会错位。路径停顿、折返时，距离到场景时间还可能是一对多关系，需要明确编辑策略。

位置：`actor/runtime/ActorPresetClock.java:24`、`ActorRuntimeController.java:841`；`ui/actor/pose/ActorAnimationEditContext.java:50`、`ActorBoneGizmoController.java:462`。

建议：共享有效动画时钟。对无法唯一反向映射的区间，提供明确的资产时间编辑模式或限制该入口，而不是悄悄退回普通片段时钟。

### C03 / P2：同一归一化时间的不同瞬时事件相互吞掉

`AnimationEventTriggerCache` 的去重键仅为 `clipId + normalizedTime`，不包含事件身份。

复现：一个动画片段在 50% 进度有两个不同事件，采样后的 `actionEvents` 数量为 1，而不是 2。第二个事件被当成已触发过的第一个事件。

重要边界：这是瞬时事件列表的问题。`ActorPropTimelineSampler` 独立重建道具状态，并使用事件序号区分同帧事件。因此不能据此断言“同时装备和投掷道具必然漏一次”。当前声音／粒子等瞬时动作的消费端仍有未接入部分，也不应把列表漏项直接描述为已经听到漏音。

位置：`timeline/playback/entity/AnimationEventTriggerCache.java:49`、`:95`。

建议：事件具有稳定身份，去重至少区分片段、事件与必要的循环实例；同时保留确定的同帧执行顺序。

### C04 / P2：动画事件时钟实际绑定片段长度，没有跟随源动画进度

动画事件模型说明其位置是动画归一化进度，但采样器使用 `(场景时间－片段起点)／片段长度`。道具重建的动画事件时间同样使用 `片段起点＋归一化位置×片段长度`。

复现：源动画长 1 秒、速度 2 倍、片段长 10 秒，50% 的投掷事件应在源动画播放到一半时出现，即约 0.25 秒；0.26 秒的事件列表实际为空，当前计算会把它放在片段第 5 秒。

相关边界：当前去重也不是按资产循环圈次组织。若未来把事件用于循环脚步或距离驱动步态，仅修正一次速度乘法仍不足够。

位置：`timeline/playback/entity/EntityClipSampler.java:464`；`actor/prop/ActorPropTimelineSampler.java:63`。

建议：区分“片段时间事件”和“源动画进度标记”。源动画标记必须和姿态采样共享速度、循环、相位及距离时钟；已有存档的事件解释需要版本兼容，不宜直接改变其发生时间。

### C05 / P2：重叠 Spawn 之间可能串入旧片段预设

较早片段 A 有 Wave；较晚片段 B 没有预设。两者重叠时，基础 Spawn 采用最后生效项 B，但预设另行在“所有有预设的 Spawn”中寻找，于是仍取得 A 的 Wave。

复现：A 为 0—5 秒，B 为 1—4 秒；第 2 秒预期当前 B 无预设，实际采样仍返回 wave。

普通属性编辑已经会拒绝一部分新产生的 Spawn 重叠。因此该问题应定位为重叠／旧数据／导入或其他创建路径下的运行时一致性缺口，不应描述为每次新建演员必然出现。

位置：`timeline/playback/entity/EntityClipSampler.java:216`。

建议：先确定当前有效 Spawn，再从同一个所有者取预设、手工修正和相关反馈。若不支持重叠，则在所有创建、复制、导入和恢复入口统一处理，而不是在某一属性面板局部拒绝。

### 本轮核对后不计为新增缺陷的项目

- `sampleSnapshot` 不触发或消耗播放事件缓存，已有隔离测试；不能把检查器查询误判成会吞播放事件。
- 道具状态不是只靠逐帧一次性事件推进，已有按时间重建、同帧排序和动画片段事件处理。
- State 属性中的潜行、疾跑和无敌目前已禁用并解释能力边界，不能再按“可点击却不生效”报告。
- 当前多动作仍主要是固定层次与 last-wins 选择；缺少任意多表演层属于能力扩展，而 C01 是现有入口已经指向不同编辑目标的正确性问题，两者需分别排期。

### 修复顺序补充

将 C01、C02 纳入首批：统一“编辑哪份数据”和“编辑哪一帧”，同时解决 A01 的详情识别。随后处理事件身份与时钟 C03/C04，以及有效 Spawn 所有权 C05。最后再增加动画标记 UI，才能避免新界面暴露一套与画面不一致的时间语义。

## 第三轮：资产入口与按通道编辑的边界

本轮继续检查关键帧复制／粘贴、循环编辑限制、通道重定时、资产绑定及撤销前置条件。新增两类问题、三个复现场景；`ActorEditingBoundaryAuditProbeTest` 的三个期望行为断言均失败。原始结果为 `build/actor-audit-results/boundary-probe-results.xml`，复现源码仍只在 build 目录。

### D01 / P2：资产库入口绕过“预设不能引用本片段手工动画”的校验

画廊的绑定服务会拒绝 `animationId == target.getBoneAnimationId()`；片段属性提交也明确拒绝这个状态。但动画资产库的“作为当前演员片段的动作预设”调用另一条服务：`ActorAnimationAssetEditing.applyPreset`。其预览和提交检查骨架与轨道，没有同样的引用约束。

复现：Spawn 的手工动画为资产 A，从资产库把 A 应用为预设，操作没有被拒绝；最终预设和手工层均引用 A。

这不是无限递归：当前合成层数固定。但同一资产可能重复参与合成；叠加模式时可能重复施加增量，草稿预览和共享引用的解释也变得困难。既然其他入口已明确定义此绑定非法，就应在共用服务中统一拒绝。

位置：`ui/actor/pose/ActorAnimationAssetPanel.java:134`、`ActorAnimationAssetEditing.java:36`；对照 `ActorPoseGalleryEditing.java:67`。

建议：所有绑定入口调用同一套验证；预览和提交时均检查，防止界面预览后上下文改变。拒绝时明确说明“这是本片段的手工修正动画”，并给出复制或选择其他动作的路径。

### D02 / P2：Root 的通道级复制粘贴未与其他编辑规则统一

#### 场景一：沿路径移动时，允许写缩放但不允许粘贴缩放

已有设计允许路径控制位置／朝向，同时单独为整体缩放打帧：`ActorRootKeyframeEditing.writeChannels` 仅在写位置或旋转时受路径保护限制。

`ActorRootKeyframeClipboard.pasteAll` 却只要存在当前路径就拒绝全部粘贴，没有检查剪贴板是否仅包含 SCALE。

复现先确认路径上写缩放键成功，再把同一片段的纯缩放键粘贴到另一时间，返回的粘贴结果为空。

用户层面的额外风险：Root 行支持按通道剪切；缩放键可以被剪切删除，但同一路径区间无法粘回目标时间，只能撤销或使用其他编辑方式。

位置：`ui/actor/pose/ActorRootKeyframeClipboard.java:29`；对照 `ActorRootKeyframeEditing.java:96`、`:101` 以及 `ui/timeline/render/ActorRootTimelineRows.java:143`。

#### 场景二：目标时间只有位置键，仍拒绝粘贴缩放键

Root UI 有按通道复制，而粘贴的碰撞检查只比较时间，不区分 POSITION／ROTATION／SCALE。只要目标时刻存在任意 Root 键，就整组拒绝。

复现：源只有缩放键，目标只有位置键，双方均使用 LINEAR，仍无法粘贴。与此相对，Root 通道重定时已经有同一时刻合并互不重叠通道的逻辑，并对插值不一致作明确拒绝。

这项应描述为通道粘贴能力缺口，不能简单称为数据损坏：目前是保守地整组拒绝，没有证据表明拒绝后会留下部分写入。

位置：`ui/actor/pose/ActorRootKeyframeClipboard.java:37`；对照 `ActorRootKeyframeTimeSession.java:108`。

建议：使用剪贴板实际通道判断路径保护；目标时刻仅有无关通道且插值兼容时可合并；真正同通道冲突或插值冲突时仍应明确拒绝或要求用户选择覆盖规则。预检整个粘贴组后再一次提交，保留当前原子性。

### 本轮确认应保留的保护

- 循环／PING_PONG 引用的关键帧重定时目前会禁用，属于主动避免一对多时间映射歧义的限制；不能直接解除按钮禁用就宣称支持循环编辑。
- 骨骼混合通道的写入、删除与移动通过分离草稿提交，并检查已有轨道身份及内容；本轮未复现“连续撤销就必然覆盖外部修改”的问题。
- 骨骼粘贴对越界和碰撞采用整组拒绝，不能在补齐 Root 通道合并时破坏这项保护。
- Root 通道重定时已有通道合并及插值冲突检查，D02 应复用其规则，而不是再增加一套不同语义。

### 截至第三轮的归纳

新增复现主要集中在四类共性：编辑目标不统一、时钟不统一、合法性校验散落在不同入口、操作粒度未贯通到通道。下一步实施应按这四条边界整理共用逻辑，再逐项把隔离用例迁入正式回归并转为通过；不宜只在各面板加单独的条件判断。
