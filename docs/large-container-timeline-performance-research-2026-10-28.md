# 大规模容器片段的时间线交互性能研究

日期：2026-10-28。源码基线：`d9d708da`。目标版本：Minecraft 1.21.10 / Fabric API 0.138.4 / Java 21。

本次完成当前源码审查和相关离线回归验证，没有修改业务代码，没有启动游戏做新的 FPS、TPS 或 GPU 测量。10 月 16 日的两份审计和日志分析仅用作历史背景，不作为当前版本的性能实测。

## 结论与目标

可以继续提高性能，而且有明确的改进空间。几十个片段、每个十万方块，不应使时间线的平移、缩放和选择操作都承担数百万方块的处理成本。应让编辑操作主要取决于可见片段和关键帧数量，让预览主要取决于当前活动动画、变化位置和可见网格分区。

当前 `TimelineClip` 通过 UUID 绑定容器，不内嵌十万方块；拖放载荷也主要是 UUID。`TimelineClipRenderer` 绘制片段、文字和关键帧，没有逐块绘制容器内容。因此，单纯重写时间线矩形绘制或更换 UI 框架不应是第一步。

但这不代表 UI 路径完全没有开销：首次拖入、松手提交、播放头定位、持续播放、补画交接和容器高亮会进入不同的重工作路径，需要分别测量。尤其不能把“几十个大容器已放在轨道上”和“几十个大容器同时做逐块动画”当成同一种负载。

## 当前已经具备的优化

- `TimelineClipBlockController.needsClipBlockUpdate()/update()` 在暂停、时间与模型未变、没有交接/追平时跳过更新，静止时间线并非每帧必然全量重算。
- 方块列表和全量集合已有缓存，EMPTY/FULL 状态能够复用集合。
- `SequenceVisibility` 使用不可变边界视图，边界不变时复用结果；时间变化不再必然复制整个可见前缀。现有测试覆盖十万位置及旧帧不可变性。
- 序列已有生成缓存；整体平移片段且长度和配置不变时，不能笼统断言会重新排序。调整长度则会使包含 `clipDuration` 的缓存失效。
- 服务端接管准备和恢复已有数量预算与 4ms 软耗时预算；提交按容器合并，集合引用相同的目标可跳过重复接收，实际恢复不依赖客户端帧率。
- section 抑制重建已有分批路径。`WholeContainerRenderView` 提供快照邻居和光照访问，它不是持久化 GPU 网格缓存。

新方案应保留这些成果，特别是异步消费者持有的旧可见集不能被后续拖动原地修改。

## 当前仍可定位的开销

### 1. 已完成片段仍可能参加逐块世界检查

位置：`TimelineClipBlockController.registerSettledContainerEntries()`，以及 `registerRenderEntriesForContainer()` 的静态分支。

已完成普通容器的全量集合虽然能复用，更新控制器时仍会遍历 `visibleBlocks`，解析期望 BlockState，并与客户端世界逐块比较。暂停且全部交接完成后，外层提前返回可以避免此成本；但播放、定位、模型变更或任一容器持续交接时，会再次更新全部相关容器。

举例：30 个已完成且可见的十万方块容器，一次控制器更新可能进入约 300 万个位置的静态检查。这是按循环规模推导的访问量，不是耗时或 FPS 实测。

建议：按容器/section 维护“静态已交接”状态。只有内容、目标、客户端区块状态或渲染抑制发生相关变化时，才重新验证该分区；持续追平只检查待交接分区。服务端已写入、客户端已收到 BlockState、客户端网格已就绪是三个阶段，不能用单一完成标志替代。

为了处理玩家外部编辑、区块卸载/重载、资源重载，应接入失效事件，并保留低频分批复核。不能一次成功后永久忽略世界变化。

### 2. 逐块动画采样仍遍历完整序列

位置：`TimelineClipBlockController.registerRenderEntriesForContainer()`。

该方法仍从头遍历整个 `sequenceEntries`，然后逐个判断可见性、动画窗口和特效条件。可见集优化不等于采样循环已变成增量；可见集变化时还有 `new HashSet<>(prevVisible)`、`new HashSet<>(renderBlocks)` 和 `removeAll()`。

建议：沿用已按时间排序的序列，通过二分边界或游标划分未开始、活动中、完成三个区间，只采样活动窗口。静态完成部分交给分区渲染/真实世界；可见性变更通过边界差量更新，不为少量变化复制整个前缀。特效起止事件独立通过时间区间游标触发，必须覆盖低 FPS 跨过多个边界、反向定位、拆除和 INSTANT 模式。

活动集本身仍可能很大。若十万方块均匀分布在 10 秒开始、每块动画持续 1 秒，活动块数量的量级仍可达一万；若开始时间集中则更高。该估算只用于说明需要活动集预算，具体取决于时间调度和效果配置。

### 3. 整体动画和静态补画仍有逐块建模成本

位置：`registerWholeContainerEntries()`、`BlockAnimationRenderer.renderEntries()/renderBlockWithAlphaAndDepth()`。

整体动画每次先给全容器写 hidden 状态，再遍历可见方块，生成快照、局部矩阵和 RenderEntry。渲染器又按片段组织临时状态映射，并逐条调用方块模型绘制。邻面剔除能减少面数，但没有消除每帧的遍历、对象分配和几何生成。

建议：用“容器内容快照 + section/材质分层网格缓存”。整体位移、旋转、缩放复用几何，只更新公共变换；按变换后的包围盒做视锥/距离裁剪。已完成但尚未落地的静态补画也复用网格。逐块独立动画保留动态活动集，完成部分并入静态分区。

先做整体动画和静态补画原型，不直接承诺全部效果均可批处理。光照/生物群系染色、AO、透明排序、方块实体、流体、资源包变化和导出确定性需要逐项验收。运动期间若要求实时环境光照，纯静态顶点缓存还需额外的光照更新策略。

### 4. 遮挡缓存命中后仍复制大型命中集

位置：`BlockOcclusionResolver.resolveOccludingBlocks()`、`TimelineClipBlockController.applyOcclusionOverrides()`。

缓存命中后仍执行 `new HashSet<>(hits)`。当前调用者遍历这些命中集，主要通过是否为空决定容器级淡化，并未逐位置应用淡化。在大量包围盒相交的场景下，缓存仍可能伴随大量分配；缓存未命中则扫描候选容器位置。

建议：为当前调用场景提供“是否命中”的轻量查询并缓存布尔结果，首次扫描遇到命中即可退出。若其他调用方需要准确位置，另保留不可变命中集接口。维持当前包围盒包含规则，性能改动不顺带改变遮挡语义。缓存按内容版本失效并受内存预算约束。

### 5. 容器高亮在网格缓存之前复制十万坐标

位置：`ContainerHighlightRenderer.render()`、`Container.getBlocks()`。

高亮开启且 ContainerManager 存在选中容器时，`render()` 先调用 `getBlocks()`，而后者返回完整 HashSet 副本；距离判断和网格缓存命中判断均在此后。因此，即使轮廓网格已缓存，仍会每帧产生 O(N) 复制；远离镜头时也先复制才返回。

这是容器高亮开启时的独立开销，不能直接说成“点击任意时间线片段都会触发”：当前片段点击同步的是 UI selection，需要区分两套选中状态。

建议：先检查数量、包围盒和距离，再查内容版本；只在构建网格时读取坐标。线程契约允许时使用只读视图，否则复用按版本生成的不可变快照。超大/稀疏容器可提供包围盒预览或分区轮廓质量档位。

### 6. 缓存失效粒度和内存上限不适合按百万位置扩展

位置：`Container.markModified()` 及其 setter；控制器的 `ContainerBlocksCache`、`ClipSequenceCache`、`enforce*CacheLimit()`。

内容缓存依赖 `modifiedTime`，而改名、颜色、锁定、透明度等也会更新该时间，导致不必要的方块列表/序列失效。时间戳使用毫秒，亦不适合作为保证每次变化可区分的严格版本号。

控制器按容器/片段数量限制缓存，而不是按方块条目、CPU 内存或 GPU 字节数限制。几十个十万方块容器仍能保留多份位置索引、序列、快照与视觉覆盖。当前不能在没有堆分析的情况下给出可靠 MB 数字。

建议：拆分单调递增的 geometry/content、BlockState/NBT、sequence、visual 和 metadata revision。序列进一步区分空间排序与时间映射，缩放片段时尽量复用排序结果；对依赖时长的序列参数逐一核对，不能强行全部共享。缓存采用按实际权重计费的 LRU，并单独限制 GPU 上传和重建队列。

### 7. 首次拖入和快速定位仍需隔离准备工作

位置：`TimelineDragAndDropHandler.handleContainerDropToTrack()`、`BlockVisualStateManager.clearOverridesFor()`、控制器的 `getCachedContainerBlocks()/getOrGenerateSequenceEntries()`。

服务端准备已经分批，但客户端仍会同步清理全部位置的视觉覆盖；首次取方块缓存要构建列表和不可变集合；首次有效动画采样要生成并排序序列。这些不受服务端 4ms 预算保护。拖入已有片段的分支也在检查 existingClips 之前清理覆盖和使控制器失效。

建议：将普通移动已有片段与首次接管分开处理，仅清理真正受影响的状态。准备工作支持版本、取消和进度；UI 先建立轻量片段，纯计算基于不可变快照后台处理，结果回主线程校验版本后发布。Minecraft 世界读取/写入、模型和 GPU 操作仍须遵守目标版本线程约束。

## 建议的实现顺序

| 阶段 | 工作 | 主要收益与验收 |
| --- | --- | --- |
| A：建立可比较基线 | 分离 UI、控制器、世界同步、三维补画计时；JFR 采集分配与 GC | 确认用户操作到底阻塞在哪一层 |
| B：先移除重复工作 | 高亮复制、遮挡命中集复制、内容版本拆分、已完成片段分区休眠 | 不改动画语义，减少稳定状态的 O(N) 工作 |
| C：动画增量化 | 活动窗口、特效游标、可见边界差量、准备取消与合并 | 逐块预览主要随活动块和变化量增长 |
| D：几何缓存原型 | 整体动画/静态补画的 section 网格，裁剪和上传预算 | 减少每帧模型处理；先做单个十万方块容器对照 |
| E：扩展与质量档位 | 多容器公平调度、缓存权重上限、交互预览质量选择 | 在 30～50 个容器下避免内存和后台队列失控 |

时间线纯滚动、缩放、悬停和选中，只需更新编辑器状态；有内容或时间变化时再请求预览。片段拖动应区分临时预览和最终提交，昂贵准备/保存不必跟随每个鼠标事件重复执行。连续预览请求保留最新版本，松手必须精确收敛。

精确预览作为默认目标。若提供简化预览，必须是明确的用户选项或质量档位，不能静默丢失方块或特效；离线导出始终以精确采样和目标帧就绪为准。单纯把逐块绘制搬进一个 Entity 不会消除这些成本，每块创建一个 Entity 也不应作为默认方案。

## 可复现的性能验收计划

固定硬件、分辨率、视距、资源包、堆大小和渲染设置；记录是否使用额外渲染模组。区块预加载与冷加载分别测试，各场景至少重复三次，预热和首次准备单独记录。

- 规模：1 / 10 / 30 / 50 个容器；每个 1万 / 10万方块。30 × 10万为重点，50 × 10万为压力场景。
- 空间：密集建筑、稀疏跨区块、互相重叠、镜头外；普通和拆除容器；高亮开/关；遮挡透明开/关。
- 操作：全部完成后暂停；播放头在所有片段左/右侧；滚动/缩放/选中；移动已有片段和调整长度；首次批量拖入；快速往返拖动播放头并松手；逐块及整体动画播放。
- 并发：顺序播放与多轨同时活动分开报告；世界恢复尚未完成时继续编辑；区块卸载重载、外部编辑、撤销重做、资源重载和导出。

记录帧耗时 p50/p95/p99、最长帧、超过 33/50/100ms 的次数、输入至片段位置更新延迟、客户端/服务端 CPU 时间、分配字节率、GC 停顿、活动/静态/待交接块数、世界写入数、section 构建/上传时间、各容器最新目标版本与完成延迟、缓存内存和队列长度。不要仅用平均 FPS 或五秒一次的最大耗时推断整场体验。

建议首轮目标：在约定机器上，30 × 10万的稳定场景中，纯编辑操作新增的 p95 CPU 开销控制在约 2ms，完整交互帧 p95 争取低于 33ms，静止场景不持续产生十万规模集合分配；这些是待基线校准的工程目标，不是已实现保证。要求定位松手后目标正确收敛，不能用漏画、错误终态或丢弃旧任务来换取短帧。

## 第一批优化实施结果

用户授权后，已完成以下代码改动：

1. **方块坐标版本独立于元数据。** `Container` 新增运行时单调递增的 `geometryRevision`；有效添加、移除、清空和克隆清理会更新版本。改名、颜色、透明度等不再导致坐标列表、空间排序、轮廓和遮挡缓存重建。可见集缓存仍单独检查容器类型和对象身份，避免普通/拆除切换或同 UUID 对象替换时误命中。存档格式未改变，原有 `modifiedTime` 继续用于其他用途。
2. **高亮取消逐帧全量复制。** 先做数量和包围盒距离判断，再读取坐标。轮廓缓存命中时不读取/哈希方块集合；非合并绘制使用当前只读视图。内容版本变化时强制生成新几何，避免仅凭集合哈希碰撞复用旧轮廓。
3. **遮挡查询改为存在性判断。** 保持原有“候选方块是否在目标包围盒内”的语义，首个命中即停止，不再保存和复制大型命中集合。按容器对缓存布尔结果，LRU 上限 1024 对；弱引用校验对象身份，避免缓存保留已删除容器的完整内容。
4. **片段时长变化复用空间排序。** 将空间评分/排序/BFS 与时间安排分开缓存。缩放片段仍重新安排批次和分层触发时间，但不重复计算空间顺序；只改单块动作时长或动作延迟也不重建序列。时间映射结果仍由原来的 `PerBlockSchedule` 产生。
5. **可见性差量按边界区间更新。** 替换复制整份可见集再做 `removeAll` 的路径。同一序列的前后边界变化直接遍历变化区间；跨序列或内容版本变化时采用无全量副本的集合差量回退。旧帧集合继续保持不可变，兼容服务端异步读取。包含重复项、缺失项和空条目的旧序列也有回归覆盖。

新增 11 项测试。最终执行 `.\gradlew.bat test --offline`，197 个测试类、1198 项测试全部通过，无失败、错误或跳过。复杂度验证中，十万方块序列从 50000 推进到 50005 时，差量路径仅访问 5 条序列记录；十万方块全部命中的遮挡查询首次只访问 1 个候选位置，元数据修改后的命中不再访问方块。这是测试内访问计数，不是游戏帧耗时或 FPS 实测。

本批次没有实现已完成容器的 section 交接休眠、逐块动画活动窗口采样或 GPU 分区网格缓存；静态世界检查和模型绘制仍可能是大场景的主要成本。为了减少缩放时的重算，空间排序缓存额外保留一份未映射条目，应在游戏内结合堆分析评估多容器内存占用；本批次没有建立按字节计费的统一缓存预算。

下一次游戏内验收应先比较高亮开/关、遮挡开/关、修改元数据、缩放片段和拖动播放头的分配率及 p95/p99 帧耗时，并检查正常/拆除容器、暂停交接与导出画面一致性。不能将全量单元测试通过视作十万方块实时播放已经验收。

## 第二批优化：序列遍历区间（2026-10-29）

已将 `registerRenderEntriesForContainer()` 的无条件全序列遍历改为区间选择：

- 利用已排序序列，对实际 `PerBlockAnimationTiming.Window` 的开始、结束时刻二分查找。直接比较最终窗口时间，避免归一化除法在临界帧的浮点舍入造成额外偏差。
- 普通 ENTER 分支不再访问尚未开始的后缀，非瞬时 EXIT 分支不再访问已经结束的前缀；已知可见性边界的集合进一步收窄渲染范围，包括瞬时拆除的可见后缀。
- 起止特效使用 `(previousTime, currentTime]` 两个边界区间，即使相应方块当前不可见，也保留低帧率跨过整段窗口时的事件处理。首次采样、预览和反向定位不额外补发事件。
- 将渲染区间和事件区间排序合并，再按原序列顺序处理；每条记录只遍历一次，仍先处理该记录的起止事件，再做原来的可见性判断和动画采样。
- TRACE 汇总改为实际注册条目计数，不再为了日志扫描整份序列。现有节流性能日志新增 `sequenceVisits`，记录当次控制器更新实际进入逐块处理循环的条目数。

新增 4 项回归，覆盖重复触发时间、精确边界及相邻浮点数、大绝对时间下的舍入、零跨度/零时长、正向/反向/停留定位、瞬时动画和起止区间重叠。最终全量运行 198 个测试类、1202 项测试，无失败、错误或跳过。

十万条序列测试中，普通片段早期的计划仅包含已开始的 3 条，拆除片段末尾仅包含剩余的 1 条；二分选择分别读取不到 50 条记录。没有可见方块且本帧只跨过少量事件时，仍能独立选中两个分离的起止区间，选择读取少于 120 条记录。这些是选择器内的访问计数，不代表整个游戏帧只处理这些位置，也不是 FPS 测量。

此批次保留完成方块的真实世界状态核对、透明/遮挡补画和动态模型采样。普通片段已开始的大型可见前缀仍可能需要逐块验证；全部完成后走静态补画的分支也仍有全量检查。因此它是“跳过不相关序列区间”，尚不是“每帧只访问正在运动的活动块”。`sequenceVisits` 不计二分查找、无序列静态回退、整体动画或实际 GPU 绘制工作，不能用它单独推断整体帧耗时。
