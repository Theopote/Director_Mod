# 大容器卡顿日志检查

检查对象：`run/logs/latest.log`、`debug.log`、`debug-1.log.gz` 至 `debug-5.log.gz`，2026-10-16 17:00～17:08 的开发客户端运行记录。本次只检查日志和对应源码，没有修改业务代码。

## 已确认的证据

1. 主耗时落在方块覆盖层绘制。latest.log:419，17:00:44，`BlockAnimations last=1345.28ms`；:456，17:01:37，721.39ms；:531，17:03:39，590.72ms；:851，17:08:23，367.10ms。渲染计时包含该回调中的 CPU 工作与日志开销，不能据此单独认定 GPU 不足。
2. 同时仍有数万方块由覆盖层绘制。latest.log:458，17:01:39，`visibleTotal=125749, seqTotal=0, renderEntries=59741`，控制器自身 total=17.12ms；:533，17:03:41，renderEntries=48733，控制器 total=16.28ms；:850，17:08:23，renderEntries=34871，total=14.86ms。说明动画序列结束后，补画交接仍长期存在，实际绘制远比控制器计算昂贵。
3. DEBUG 日志严重刷屏。当前保留的六份 debug 文件覆盖 17:07:46～17:08:41，约 55 秒，共有 4,866,156 条 `applyAnimationTransformFromSnapshot` 日志，几乎全部为正常的 `snapshot.getTransform() is null` 路径。五个压缩分卷分别约 95.7 万行，只覆盖 10～11 秒；debug.log 又有 79,889 条。不能把正常的单位变换当作逐方块调试异常记录。对应 `BlockAnimationRenderer.java:315`。
4. 同一批 debug 文件出现 456 次 `光照刷新跳过: Ran automatically on a different thread!`，由 `ContainerVisibilityService.flushLightingForChunks()` 直接调用 `getLightingProvider().doLightUpdates()` 后捕获异常记录，位置约 :612。已确认这条强制刷新路径不能按预期执行；这不等于 Minecraft 自己的异步光照也全部失败。
5. 大规模重渲染请求反复被整体丢弃。latest.log:406 为 125749，:418 为 110955，:551 为 96923，:574 为 122939 个方块。源码在超过 MAX_RERENDER_BLOCKS 时直接清空 rerender 集合。抑制状态切换此前会另交给 WholeContainerRenderSections，因此不能仅凭这些警告断言所有区块重建都被丢失；但当前策略缺少明确的分批完成反馈。
6. 本次 latest.log 没有 `Can't keep up`。ERROR 是用户属性/Realms 网络获取失败，未看到对应的容器异常。日志没有服务端 tick 和光照队列耗时采样，不能据此排除服务端或光照积压。

## 与源码共同指向的放大链路

上一轮修复为避免方块消失，让尚未落地的方块继续补画；这些正常静态补画进入逐方块 DEBUG 日志路径，把原先就昂贵的逐块模型绘制进一步放大。这一影响在上一轮单元测试中没有覆盖。

当前普通播放恢复仍受客户端每帧预算控制，默认单容器 64 个新增方块。在日志中的约 1.5 FPS 下，理论提交上限仅约 96 个/秒；这不是服务端吞吐实测。帧率降低会延长真实方块恢复时间，使数万补画条目持续存在，形成“补画多 → 绘制与日志更慢 → 恢复目标推进更慢 → 补画长期存在”的反馈。17:01:39 至 17:03:57，补画条目从 59741 降到 47204，与这种缓慢交接现象一致，但中间用户操作未被完整记录，不能作为严格吞吐基准。

阴影更新慢可能同时受到低帧率、真实方块恢复缓慢、光照/区块网格异步更新的影响。当前强制光照刷新调用报错是明确问题，但还不能把它认定为唯一原因。

## 后续处理优先级

1. 移除正常静态补画路径的逐方块 DEBUG 输出，保留节流汇总；先复测其对 BlockAnimations 回调耗时的影响。
2. 世界恢复调度与客户端 FPS 解耦，按服务端 tick 和耗时预算推进；不能靠单纯提高客户端每帧限额补救。
3. 核对目标版本光照提供器的正确调度方式，消除反复异常的强制调用；补齐光照积压、实际写入数、待恢复数与最老目标年龄的采样。
4. 重建请求按 section 去重、分批处理并跟踪完成，不通过静默丢弃来限流。
5. 对静态补画/整体动画建立分区网格缓存，避免数万方块每帧重新取模型、计算光照并生成几何。逐块活动动画另行限制活动集。

当前证据足以先处理日志、调度和光照调用，尚不足以估算每项优化后的帧率收益。

## 本轮已实施修复

- 移除 `BlockAnimationRenderer` 正常静态姿态和缺失快照分支的逐方块 DEBUG 输出；静态单位矩阵直接返回。
- `TimelineClipBlockController` 提交当前时间采样得到的完整世界目标，删除客户端每帧追加数量限流及其全量集合复制、待追加位置排序。实际写入仍由服务端数量/软耗时预算控制；单次客户端提交后，服务端可以独立继续收敛。
- 核对本地 Minecraft 1.21.10 映射源码：`ServerLightingProvider.doLightUpdates()` 明确无条件抛异常；`WorldChunk.setBlockState()` 已经排队必要的方块/section 光照检查。现在每个 tick 按世界合并调度 `ServerLightingProvider.tick()`，由原生光照线程执行，不再调用必然失败的同步入口，也不重复逐格 checkBlock。
- 删除超阈值清空重渲染请求和按方块包围盒重复重建的路径。只对世界渲染抑制状态的切换请求 section 重建；透明度变化由覆盖层处理，实际世界方块变动使用原生更新。
- 发现并限制另一个同步热点：原 WorldRendererMixin 会同步重建全部请求 section 并上传。现在去重队列每帧最多处理 2 个 section，软耗时预算 2ms，未处理请求保留；渲染器尚未就绪时不取走请求。单个原生重建/上传仍可能超过软预算，不能承诺帧耗时硬上限。非驻留 section 没有旧网格，后续正常构建会读取当前抑制状态。
- 新增节流统计：服务端 `[Perf][ContainerVisibility]` 记录实际世界写入数、预算使用、处理耗时峰值、准备/转换/恢复队列数、最老目标年龄和光照调度次数；客户端 `[Perf][ContainerSections]` 记录重建数、剩余 section 和批次耗时峰值。两者最多每五秒记录一次活动统计。

新增 4 项回归：无新客户端帧时恢复继续推进；100 个 section 分 50 帧完整处理；超时/未就绪请求不丢失；跨帧去重与切世界清理。

针对本轮的 45 项相关测试通过。全量运行 933 项，932 通过，唯一失败仍是原有 ActorBoneDraftTransactionTest 反射访问不存在的 createdAnimationClip 字段。本次未修改该测试及演员控制器。

尚未进行修复后的游戏内 FPS、光照收敛与视觉交接复测，也未实现分区网格缓存。同步重建改为分批后，大量渲染抑制切换会跨帧完成，需重点检查期间的临时画面残留/交接；不能把单元测试通过当作画面已验收。逐块模型绘制的剩余成本仍需以新日志判断。

### 剩余问题及证据

1. **偶发绘制尖峰仍明显。** latest.log:440，17:19:13，BlockAnimations last=188.19ms；:458，17:19:38，127.53ms；:471，17:19:53，282.21ms。同一轮控制器 15 个定时样本的中位数为 4.21ms，最大 53.27ms 出现在初次进入。渲染器警告样本有筛选偏差，不能以其均值或中位数作为整场平均帧耗时。
2. **大集合转换和扫描可能产生不必要工作。** 17:19:36，converting=1、working=0、submitted=1，oldestTargetMs=5901；17:19:41 为 converting=1、working=1、oldestTargetMs=10950；17:19:46 恢复为空。对应代码只按集合引用跳过重复转换；逐块采样在时间变化时会创建新的前缀集合，即使边界没变或已经全显，引用也可能变化。服务端每个工作扫描还会遍历 shown 和 target。需要通过目标版本、相同边界缓存、转换丢弃计数和各阶段独立计时验证。oldestTargetMs 表示持续待处理容器的任务年龄，不是最新请求的精确延迟。
3. **面板整体任务尚未遵守耗时预算。** 17:18:15 的服务统计 maxTickMs=26.88，17:18:55 的累计统计为 20.94；debug 同时记录进入时三个容器的隐藏任务。源码 pendingTasks 循环只检查数量预算，task.process(budget) 内也不检查 deadline，确实可能使服务处理超过 4ms。不能把这两个采样尖峰全部归因于该路径，首次加载/JIT 等也可能参与。
4. **section 队列仍有短时积压，但没有从这些采样中看到单调失控增长。** pending 样本为 0～40；记录的批次耗时峰值 2.08～8.59ms，说明单个同步原生重建可突破 2ms 软预算。17:19:26 pending=0，17:19:58 又为 39，不能仅凭间隔样本认定始终已清空或始终积压。继续关注光照刷新时的网格交接画面。
5. **逐帧 UI 日志仍较多。** 新 debug.log 约 10MB；WorldIdentifier 两类日志各约 1.02 万条，PropertyAdapterRegistry 兼容匹配约 1.02 万条，ImGui 每个固定帧日志约 5117 条。量级已远低于之前 55 秒 486 万条，但正常帧路径仍有可移除的日志。当前没有计时证据表明它们是剩余主瓶颈。

### 下一轮优先级

先补齐目标转换/恢复的版本与分阶段统计，缓存可见前缀边界未变化或已经全显时的稳定集合，避免为同一结果重新转换整个目标；同时让面板任务使用同一耗时预算。随后针对静态补画的逐块模型几何开销做分区缓存和裁剪。UI 日志可作为独立的小幅减负项，不应替代主渲染路径优化。

新一轮主要是约 4.87 万可见方块，前一轮曾达到约 12.57 万；操作顺序也不同，因此上述日志不构成相同负载的严格性能对照，不能直接计算优化百分比。
