## 1. 结论摘要

Director 的 UI 已经形成较完整的编辑器骨架：`DirectorScreen` 负责 Minecraft Screen 生命周期，`DirectorUIManager` 协调 DockSpace 和面板，`AbstractPanel` 统一窗口与样式边界，输入 Mixin 负责把主窗口事件单次投递给 ImGui，属性面板通过选择服务切换上下文，容器树和时间线也已有较明确的交互分层。

当前最值得优先处理的是三类问题：

1. **跨世界布局隔离失效**：切档时旧世界布局会写入新世界目录，并覆盖新世界原有布局。
2. **UI 生命周期清理不完整**：容器面板关闭后仍被全局管理器持有；属性面板尝试移除监听器，但因方法引用身份不同实际没有移除。
3. **ImGui 异常恢复边界不完整**：外层渲染异常不保证调用 `endFrame()`，自定义栈清理不能结束原生 ImGui 帧。

本次共整理 **16 项新问题**：

- **P1：3 项**。涉及跨世界布局覆盖、初始化失败页无法按提示退出、异常路径可能破坏 ImGui 帧状态。
- **P2：10 项**。涉及监听器泄漏、预设数据冲突、容器树性能、演员创建反馈、detached 输入、预设语义、快捷键穿透、设置 Cancel 和原生栈异常安全。
- **P3：3 项**。涉及默认窗口尺寸时机、加载布局弹窗每帧磁盘扫描、通用设置弹窗完成度。

建议先修复布局和监听器生命周期，再建立可靠的 ImGui 帧异常恢复，随后处理 detached 输入与对话框事务语义，最后做容器树和弹窗的每帧性能优化。

## 5. P1 问题

### UI-01 世界布局路径忽略 worldId，切档会覆盖新世界布局

**优先级**：P1  
**证据**：已复现

**位置**

- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:137-153`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:180-208`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:215-231`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:298-315`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:330-347`

**问题**

`getLayoutFile(String worldId)` 和 `getImGuiIniPath(String worldId)` 都没有使用 `worldId`，而是每次通过 `getLayoutsDir()` 读取当前的 `WorldIdentifier.getWorldSavePath()`。

切档时 `reloadForCurrentWorld()` 的顺序是：

1. 使用旧 `currentWorldId` 调用 `saveLayoutForWorld()` 和 `saveImGuiIni()`。
2. 把 `currentWorldId` 更新为新世界。
3. 加载新世界布局。

但此时 `WorldIdentifier.getWorldSavePath()` 已经指向新世界，因此第 1 步实际把旧世界状态写入新世界目录。随后第 3 步又从刚被覆盖的新世界文件加载。

**影响**

- 旧世界退出前的布局没有保存到旧目录。
- 新世界原有 `ui_layout.json` 和 `imgui.ini` 被旧世界状态覆盖。
- 用户切回旧世界时可能看到更早的布局，进入新世界时看到旧世界布局。
- 该问题发生在正常切档路径，不依赖异常或大数据量。

**修复方向**

- 在切档前解析并保存旧世界的 `Path`，切档后再解析新世界路径。
- 让 `getLayoutFile(worldId)` 真正按 worldId 路由，或显式传入 `Path`，避免路径解析依赖可变的全局当前世界。
- 保存旧世界时使用旧路径快照；加载新世界时使用新路径快照。
- 对写入目标增加当前世界校验，防止全局状态在保存过程中变化。

**回归验证**

准备两个临时世界目录，各自写入不同布局和 INI；从 A 切到 B，断言 A 文件仍保存在 A、B 文件未被 A 覆盖；再切回 A，验证两边状态独立。

### UI-02 初始化失败页提示 ESC 关闭，但实际无法通过 ESC 退出

**优先级**：P1  
**证据**：强代码证据，条件性

**位置**

- `src/main/java/com/director/ui/DirectorScreen.java:136-169`
- `src/main/java/com/director/ui/DirectorScreen.java:294-315`
- `src/main/java/com/director/ui/DirectorScreen.java:586-621`
- `src/main/java/com/director/mixin/KeyboardMixin.java:94-107`
- `src/main/java/com/director/client/DirectorClient.java:205-209`

**问题**

UI 管理器构造失败时，`DirectorScreen` 显示错误页并提示“按ESC键关闭此屏幕”。但：

- `shouldCloseOnEsc()` 固定返回 `false`。
- `keyPressed()` 没有为 `initializationFailed` 提供显式 `close()` 分支。
- `KeyboardMixin.dispatchDirectorShortcut()` 在 `uiManager == null` 时直接返回。
- 打开 Director 的全局键绑只在 `currentScreen == null` 时处理，错误页打开期间不能再次切换。

**影响**

当 UI 管理器初始化失败但 ImGui 本身已初始化时，用户进入错误页后无法使用界面提示的方式返回游戏，只能依赖外部强制结束或重启客户端。

**修复方向**

- `shouldCloseOnEsc()` 在 `initializationFailed` 时返回 `true`。
- 或在 `keyPressed()` 中检测 ESC 并显式调用 `close()`。
- 错误页提供可点击的“返回游戏”按钮作为第二出口。
- 对关闭失败保留日志，但不要继续显示不可退出的全屏页面。

**回归验证**

注入 `UIConfiguration.createUIManager()` 失败，进入错误页后按 ESC，断言 Screen 关闭且世界、相机和输入状态完成恢复。

### UI-03 外层渲染异常不保证结束 ImGui 帧

**优先级**：P1  
**证据**：强代码证据，条件性，需实机确认

**位置**

- `src/main/java/com/director/ui/DirectorScreen.java:219-289`
- `src/main/java/com/director/ui/imgui/ImGuiRenderer.java:238-277`
- `src/main/java/com/director/ui/imgui/ImGuiRenderer.java:393-415`
- `src/main/java/com/director/ui/imgui/ImGuiStateChecker.java:207-223`

**问题**

`DirectorScreen.render()` 在 `beginFrame()` 成功后，把 `endFrame()` 放在正常路径末尾，而不是 `finally` 中。以下任一步抛错都会跳过 `endFrame()`：

- `DirectorStyleScope.enter()` 或作用域关闭。
- `uiManager.render()` 中未被面板隔离的全局弹窗、DockSpace 或协调代码。
- `InputFocusManager.update()`。
- `ImGuiCursorController.applyToImGui()`。

异常处理只调用 `ImGuiStateChecker.forceCleanupStack()`，该方法仅清空自定义 `ThreadLocal` 记录，不调用 `ImGui.render()` 或恢复原生窗口、样式、树和 popup 栈。

同时 `ImGuiRenderer.beginFrame()` 在 `frameInProgress == true` 时返回 `true`，调用方会继续渲染，而不是跳过本帧。

**影响**

- 原生 ImGui 帧可能跨帧保持未结束状态。
- 后续 `Begin()` 可能在同一帧内重复提交，或触发原生断言和状态错乱。
- 自定义检查栈被清空后，真实原生栈不平衡可能被掩盖。
- 异常持续发生时，UI 可能无法自行恢复。

**修复方向**

- 用 `boolean frameStarted` 和 `finally` 保证 `endFrame()` 只调用一次。
- `beginFrame()` 在 `frameInProgress` 时返回 `false`，要求调用方跳过渲染。
- 自定义栈清理不能替代原生恢复；异常恢复应至少结束当前帧，必要时重建上下文。
- 对无法可靠恢复的原生状态采取“停止本帧 UI + 下次重建”的策略，而不是继续在未知栈上渲染。

**回归验证**

在 `beginFrame()` 后分别注入 `uiManager.render()`、焦点更新和光标更新异常，断言 `frameInProgress == false`、原生帧已结束、下一帧可重新开始且无断言错误。

## 6. P2 问题

### UI-04 ContainerPanel 注册全局监听器但没有移除

**优先级**：P2  
**证据**：已复现

**位置**

- `src/main/java/com/director/ui/panels/ContainerPanel.java:66-80`
- `src/main/java/com/director/core/container/ContainerManager.java:53`
- `src/main/java/com/director/core/container/ContainerManager.java:1363-1377`
- `src/main/java/com/director/ui/DirectorUIManager.java:1002-1022`
- `src/main/java/com/director/ui/panels/AbstractPanel.java:285-289`

**问题**

`ContainerPanel` 构造器调用 `containerManager.addListener(this)`，但没有 override `dispose()`，也没有调用 `removeListener(this)`。

`DirectorUIManager.dispose()` 会调用面板的 `dispose()`，但 `ContainerPanel` 继承的是 `AbstractPanel` 的默认实现，只把 `initialized` 置为 `false`。全局 `ContainerManager.listeners` 是 `CopyOnWriteArrayList`，会继续持有旧面板。

**影响**

每次关闭并重新打开 Director，旧 `ContainerPanel` 都可能留在全局监听器列表中，连同其 state、controller、tree view、dialogs、属性面板和命令历史一起保留。监听器数量随打开次数线性增长，并增加每次容器事件的遍历和日志开销。

**修复方向**

- 在 `ContainerPanel.dispose()` 中调用 `containerManager.removeListener(this)`。
- 清理子组件和面板持有的状态引用。
- 为所有注册全局监听器的面板建立统一生命周期检查或测试。
- `dispose()` 保持幂等，避免重复移除和重复清理。

**回归验证**

连续创建并销毁 10 个 `ContainerPanel`，断言容器监听器数量回到基线；用弱引用或堆转储确认旧面板及子对象可被 GC。

### UI-05 PropertiesPanel 添加和移除使用不同方法引用对象，监听器移除无效

**优先级**：P2  
**证据**：已复现

**位置**

- `src/main/java/com/director/ui/panels/PropertiesPanel.java:187-195`
- `src/main/java/com/director/ui/panels/PropertiesPanel.java:549-557`
- `src/main/java/com/director/ui/selection/SelectionManager.java:351-367`

**问题**

构造器注册：

```java
addSelectionChangedListener(this::onSelectionChanged);
```

`dispose()` 移除：

```java
removeSelectionChangedListener(this::onSelectionChanged);
```

这两个方法引用表达式会生成不同的 `Consumer` 对象。`SelectionManager` 使用 `List.contains/remove` 的对象相等语义，没有按方法或 owner 匹配，因此移除调用通常无法匹配注册时保存的对象。

**影响**

旧 `PropertiesPanel` 仍被全局选择服务持有。每次选择变化都会调用旧面板回调，造成对象保留、重复更新和潜在性能增长。探针中监听器数量为 `1 -> 2 -> 2`，确认 `dispose()` 后没有减少。

**修复方向**

- 把监听器保存为字段，例如 `private final Consumer<Object> selectionListener = this::onSelectionChanged;`，添加和移除都使用同一对象。
- 或让监听器 API 支持稳定 token/owner。
- 增加“构造后 dispose，监听器数量恢复基线”的生命周期测试。

**回归验证**

重复打开/关闭属性面板，断言监听器数量不增长；触发选择变化时，只有当前面板收到回调。

### UI-06 布局预设名称有损清理，不同名称会静默覆盖

**优先级**：P2  
**证据**：已复现

**位置**

- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:427-457`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:470-487`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:504-523`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:553-557`

**问题**

预设文件名仅使用：

```java
name.replaceAll("[^a-zA-Z0-9_\\-]", "_").toLowerCase()
```

`LayoutData` 不保存原始显示名，列表又直接从文件名还原名称。空格、下划线、大小写和不同中文字符都可能映射到同一文件名。保存时使用 `Files.writeString()` 直接覆盖，没有冲突提示。

探针中 `视觉布局` 和 `声音布局` 均得到 `____`。

**影响**

- 中文预设名在列表中显示为下划线，难以识别。
- 不同用户预设可能互相覆盖，且没有警告。
- 用户无法从列表恢复原始名称。
- 删除一个预设时可能误删另一个映射到同一文件的预设。

**修复方向**

- 使用稳定 UUID 或文件名安全编码作为文件名，把原始名称保存在 JSON 中。
- 保存前检查同名或同编码冲突，要求用户确认覆盖。
- 列表显示 `LayoutData.displayName`，而不是文件名。
- 为旧文件提供迁移或兼容读取。

**回归验证**

保存 `视觉布局`、`声音布局`、`Layout A`、`layout_a` 等名称，断言文件独立、列表显示原名称、覆盖需确认、删除只影响目标预设。

### UI-07 容器树每个节点重复扫描全部时间线片段

**优先级**：P2  
**证据**：强代码证据，性能风险

**位置**

- `src/main/java/com/director/ui/container/ContainerTreeRenderer.java:124-134`
- `src/main/java/com/director/ui/container/ContainerTreeRenderer.java:533-534`
- `src/main/java/com/director/ui/container/ContainerTreeInteractionHandler.java:278-280`
- `src/main/java/com/director/ui/container/ContainerTreeInteractionHandler.java:627-639`
- `src/main/java/com/director/timeline/container/ContainerTimelineService.java:87-123`

**问题**

每个容器节点渲染时都会调用 `isContainerOnTimeline(containerId)`。该方法的实现是：

```java
return !findClipsForContainer(containerId).isEmpty();
```

`findClipsForContainer()` 每次创建新列表，并遍历所有 CONTAINER 轨道及其全部片段。悬浮提示还会再次调用同一检查。

右键菜单中的 `isTimelineControlled()` 会递归检查子树，多个菜单项、批量选择、目标组收集又会重复调用，进一步放大扫描次数。

**影响**

设可见容器节点数为 C、容器片段数为 K，则基础树渲染约为 `O(C × K)`，且每次查询伴随列表分配。节点和片段规模增大后，容器树会成为明确的每帧热点；打开右键菜单后复杂度还会进一步提高。

**修复方向**

- 每帧构建一次 `Set<UUID> onTimelineContainerIds`，树渲染直接查询集合。
- 或由 `TimelineModel` 维护绑定索引，在片段增删和绑定变化时更新。
- 提供不分配列表的 `hasClipsForContainer()`。
- 右键菜单在一次打开期间缓存 `isTimelineControlled()` 结果。
- 搜索树每帧复制 roots 和递归匹配属于次要分配，可后续合并优化。

**回归验证**

构造 1000 个容器节点和 1000 个容器片段，比较优化前后每帧扫描次数、分配量和帧时间；断言右键菜单不会再次线性扫描全部片段。

### UI-08 演员放置失败只写日志并关闭弹窗

**优先级**：P2  
**证据**：强代码证据

**位置**

- `src/main/java/com/director/ui/actor/ActorSelectorPanel.java:111-115`
- `src/main/java/com/director/ui/actor/ActorSelectorPanel.java:147-158`
- `src/main/java/com/director/ui/actor/placement/ActorPlacementController.java:95-131`

**问题**

“创建”按钮无条件关闭弹窗。`createActorAndTrack()` 只记录 `startPlacement()` 的布尔结果，失败时没有界面反馈。

`startPlacement()` 会因客户端/世界未初始化、时间线模型为空、正在播放、正在 scrubbing、预览实体创建失败或运行时异常而返回 `false`。

**影响**

用户点击创建后只看到弹窗消失，无法判断演员是否已进入放置模式，也得不到“请先停止播放”等原因。容易重复点击或误以为功能故障。

**修复方向**

- 让创建操作返回明确的结果或失败原因，而不是只有布尔值。
- 失败时保持弹窗并显示 `InlineNotice`，或关闭弹窗但发送统一状态栏通知。
- 对播放、scrubbing、预览失败分别提供可理解的文案。
- 成功时显示“点击场景放置演员，ESC 取消”的提示。

**回归验证**

分别在播放中、scrubbing 中、模型为空和预览失败时点击创建，断言用户可见反馈与日志原因一致，且不关闭唯一操作入口。

### UI-09 detached 窗口共享全局 ImGuiIO，可能错误拦截主窗口游戏输入

**优先级**：P2  
**证据**：需实机确认

**位置**

- `src/main/java/com/director/ui/window/DetachedDirectorWindow.java:138-160`
- `src/main/java/com/director/ui/window/DetachedDirectorWindow.java:228-250`
- `src/main/java/com/director/ui/imgui/ImGuiRenderer.java:253-285`
- `src/main/java/com/director/ui/DirectorScreen.java:370-373`
- `src/main/java/com/director/mixin/MouseMixin.java:57-62`
- `src/main/java/com/director/mixin/MouseMixin.java:133-146`
- `src/main/java/com/director/mixin/KeyboardInputMixin.java:48-52`

**问题**

detached 窗口打开时，`prepareFrame()` 会覆盖共享 IO 的 display size、mouse position 和 mouse button 状态。主窗口的 `DirectorScreen.isMouseOverDirectorGui()`、`MouseMixin` 和 `KeyboardInputMixin` 又直接读取同一个 `ImGuiIO.wantCaptureMouse`。

与此同时，`shouldFeedMinecraftInput()` 在 detached 打开时禁止主窗口 Mixin 向 ImGui 投递事件。这造成输入状态来源和主窗口游戏输入门控可能不一致。

**影响**

如果 detached 指针位于其 UI 上，而用户把焦点切回 Minecraft 主窗口，主窗口点击、滚轮或移动输入可能被 detached 的捕获状态错误拦截；反向情况下也可能出现 UI 与游戏输入同时响应。具体表现取决于 GLFW 焦点、坐标和后端更新顺序。

**修复方向**

- 按窗口维护输入归属和捕获状态，不使用单一全局 `wantCaptureMouse` 决定主世界输入。
- 主窗口游戏输入至少检查主窗口是否 focused/hovered，以及主窗口坐标是否命中主视口 UI。
- detached 输入只影响 detached 窗口，主窗口 Mixin 在 detached 打开时明确走游戏输入放行逻辑。
- 为双窗口焦点切换建立明确的状态机。

**回归验证**

同时打开主窗口和 detached 窗口，交替聚焦两者，在 detached UI、主窗口 UI 和世界空白处分别测试点击、滚轮、WASD 和中键视角，断言只有目标窗口响应。

### UI-10 布局预设只保存面板可见性，不保存 DockSpace 几何

**优先级**：P2  
**证据**：强代码证据

**位置**

- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:56-82`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:427-455`
- `src/main/java/com/director/ui/layout/LayoutPersistenceManager.java:470-487`

**问题**

`LayoutData` 只有 `panels` 和 `worldFingerprint`，没有 DockSpace 节点、窗口位置或尺寸。保存预设时只复制 `currentLayout.panels`。

加载预设后调用 `saveImGuiIni()`，保存的是当前 ImGui 状态，而不是预设中的几何，因为预设根本没有保存几何。

**影响**

- 加载完整预设时先应用几何，再保存；可见性预设不要覆盖当前 INI。
- UI 文案和确认框说明预设包含哪些内容。

**回归验证**

保存两个停靠结构和尺寸明显不同的布局，加载第一个后断言节点、位置和大小均恢复；加载纯可见性预设时断言当前几何不变。

### UI-11 SelectionHistoryPanel 的 Ctrl+Z/Y 缺少焦点和文本输入保护

### UI-12 时间线设置对话框立即应用，Cancel 不恢复原值

**优先级**：P2  
**证据**：强代码证据

**位置**

- `src/main/java/com/director/ui/dialogs/DialogManager.java:217-277`
- `src/main/java/com/director/ui/dialogs/DialogManager.java:285-361`

**问题**

帧率、时间单位、吸附开关和吸附参数在控件变化时立即写入模型或 `TimelineSnapSettings`。“确定”和“取消”都只调用 `closeTimelineSettingsDialog()`，没有提交/回滚语义。

### UI-13 容器树和菜单的部分原生样式/树栈缺少 finally 保护

**优先级**：P2  
**证据**：强代码证据，条件性

**位置**

- `src/main/java/com/director/ui/container/ContainerTreeRenderer.java:137-204`
- `src/main/java/com/director/ui/container/ContainerTreeRenderer.java:286-294`
- `src/main/java/com/director/ui/container/ContainerTreeRenderer.java:428-494`
- `src/main/java/com/director/ui/container/ContainerTreeInteractionHandler.java:294-320`
- `src/main/java/com/director/ui/container/ContainerTreeInteractionHandler.java:517-615`
- `src/main/java/com/director/ui/dialogs/DialogManager.java:222-364`

**问题**

容器树节点的 `pushStyleVar`、选中态 `pushStyleColor`、`treePop()`、`beginDisabled/endDisabled` 都主要在正常路径配对，没有完整放在 `finally` 中。右键菜单和弹窗也存在同类模式。

`AbstractPanel` 和 `ImGuiUtils` 的窗口 Begin/End 已有较好保护，不能笼统说所有面板都会泄漏；这里指的是容器树和菜单内部的局部原生栈。

- `treePop()` 在成功 `treeNodeEx` 后于 `finally` 中调用。
- 弹窗和菜单的 `endPopup/endMenu` 使用统一安全封装。
- 与 UI-03 的帧级恢复配合，但不要依赖全局清栈代替局部平衡。

**回归验证**

在树节点、菜单项和弹窗控件中注入异常，断言所有样式、disabled、tree 和 popup 栈深度恢复，后续面板渲染状态正常。

### UI-14 AbstractPanel 在 Begin 之后设置默认窗口尺寸

**优先级**：P3  
**证据**：需实机确认

**位置**

- `src/main/java/com/director/ui/panels/AbstractPanel.java:149-169`
- `src/main/java/com/director/ui/panels/AbstractPanel.java:349-359`

**问题**

`renderWindowContent()` 在窗口 `Begin()` 已经执行后，根据 `isWindowAppearing()` 调用 `setDefaultWindowSize()`，后者使用 `ImGui.setNextWindowSize()`。

`setNextWindowSize()` 通常作用于下一次 `Begin()`，因此在当前窗口内容阶段调用时，首次默认尺寸可能延迟一帧或不生效。

**影响**

**修复方向**

- 在 `ImGui.begin()` 之前根据面板首次出现状态设置尺寸。
- 或由 DockSpace 布局构建器统一提供首次尺寸。
- 实机验证首次打开、隐藏后重新打开和重置布局三种路径。

**回归验证**

首次打开每个活动面板，断言首帧尺寸符合预期；隐藏后重新打开不重置用户已调整尺寸。

### UI-15 加载布局弹窗每帧扫描预设目录

## 9. 值得保留的实现

- `ImGuiUtils.beginWindow()` 正确处理 `Begin()` 返回 false 时仍需调用 `End()`。
- `AbstractPanel` 的窗口结束和样式 pop 已有 `finally` 保护。
- `InputFocusManager` 在 Director Screen 不活跃时重置捕获状态。
- 主窗口 ImGui 输入由 Mixin 单次投递，避免 GLFW 回调重复字符。
- `ContainerPanel` 快捷键已有窗口焦点和 `WantTextInput` 保护。
- `MenuBarPanel` 延迟关闭 Screen，避免在 DockSpace 栈未结束时直接销毁界面。
- 容器树行内图标点击优先 consume，避免误触发行选择。
- 容器树批量拖放统一走 `controller.moveContainers(...)`，一次 drop 对应一条移动命令。
- `StatusBarPanel`、`ToolbarPanel` 的关键样式栈有 finally 平衡，FPS 使用平滑值。
- `InlineNotice` 提供统一的图标、颜色和换行，可作为演员创建失败、设置错误等反馈的统一入口。
- `PropertyContextService` 使用静态注册标志保证选择监听器单次注册，是合理的全局单例监听器模式。
